# 005 Scroll Snap, Full-Screen Sections, Hero, Navbar, Section Arrows and Fixed Canvas

## Summary
Round 1 of the UX/UI pass (round 2 is spec 006). The home page scrolls section by section on desktop-size windows: one wheel, trackpad or key input animates to the next or previous full-screen section, further wheel/key input is ignored until the move and the trackpad inertia tail are over, and any non-snap scroll settles to the nearest section once idle. Deliberate clicks (navbar links, section arrows, hash navigation) interrupt and retarget a running move. Two fixed arrow controls (down at bottom-centre, up at top-centre, one shared SVG) replace the Hero CTA and any back-to-top button; they exist only while snapping is active. The navbar stays in flow and scrolls away with the Hero, loses the "Tech Stack" link, and gets a hamburger menu on phone widths. The Hero moon is 90% of its current size, scales with the window with a small-screen floor and side-margin ceiling, plays a 3 s "approach" intro before the text intro, and hero text wraps around it. The page-tall WebGL canvas becomes a viewport-fixed canvas so buffer size and render cost stay constant and DPR reaches the device value.

## Baseline (current code, brownfield on 002 to 004)
- `src/App.jsx`: shell `flex min-h-svh flex-col`; `Navbar` (normal flow, not sticky), `ScrollToHash`, `main > Routes`. `src/main.jsx` wraps the app in `StrictMode`, `BrowserRouter`, `SmoothScrollProvider`.
- `src/components/Navbar.jsx`: one row, always visible, `flex-wrap`; items: brand "Himar", Home, Projects (`/#projects`), About (`/#about`), Tech Stack (`/#tech-stack`), 3D Viewer. Height 61 px at desktop (44 px item + 16 px padding + 1 px border = `3.8125rem`).
- `src/pages/HomePage.jsx`: `relative isolate` wrapper holding the lazy `PageCanvas` (unless reduced motion), then `Hero`, `Projects`, `AboutMe`, `TechStack`.
- `src/three/PageCanvas.jsx`: a page-tall canvas, `absolute inset-0 -z-10`, `maxHeight = probe.maxDim`, orthographic, 1 world unit = 1 CSS px, `DprController` sets DPR with `computeDpr` (`DPR_MAX = 2`, `PIXEL_BUDGET_DESKTOP = 16M`, `PIXEL_BUDGET_COARSE = 8M`, `src/three/bufferLimits.js`); `scripts/check-buffer-limits.mjs` (`npm run check:buffer`) tests page-tall sizes. `PageScene.jsx` scrolls stars with `useScrollMetrics` (`window.scrollY`, bounded offset up to 120 px) plus drift and pointer parallax; the moon sits at the Hero box centre in page coordinates (`useHeroMetrics`, cached `offsetLeft/Top/Height` from a `ResizeObserver`) with radius `moonRadiusPx(heroHeight)` = `0.3972 x heroHeight` (`moonFraming.js`). At 1920x1080 the Hero is about 1019 px tall, so the current radius is about 405 px (diameter about 810 px); at 375x812 the diameter is about 596 px. At 1920x1080 the page-tall canvas would grow with full-screen sections (about 4 x 1080 px), which cuts DPR via the pixel budget.
- Sections: `Hero` is `min-h-[calc(100svh-3.8125rem)]`, text column left (`lg:max-w-md xl:max-w-lg lg:pl-12`), poster `<img>` in `[data-stage]` (`object-contain`, `inset-0`), CTA link "View projects" to `/#projects`. `Projects`, `AboutMe`, `TechStack` are content-sized (`py-16 md:py-24`, `max-w-5xl`), ids `projects`, `about`, `tech-stack`, with one-shot `useSectionReveal` (`top 80%`) and `SplitHeading` (`top 85%`) reveals. All three are shorter than one screen at desktop sizes today.
- Hero intro (`Hero.jsx`): module flag `introPlayed`; GSAP timeline of about 2.0 s (eyebrow, heading words, paragraph, CTA, then `[data-stage]` fade/scale from 0.94). Skipped with reduced motion. Poster and live canvas crossfade (`canvasStatus`: `idle`, `live`, `fallback`).
- Scroll: `SmoothScrollProvider` creates one Lenis instance (not with reduced motion), driven by `gsap.ticker`, feeding `ScrollTrigger.update`. `ScrollToHash` calls `lenis.scrollTo(el, { offset: 0 })` or `el.scrollIntoView()`.
- `src/lib/gsap.js` is the single GSAP/ScrollTrigger registration point. `usePrefersReducedMotion` is the reduced-motion hook.

## Goals
- Section-by-section desktop scrolling that is predictable: never skips, never double-jumps, never traps the user, always rests on a section.
- Every section fills one screen at 1920x1080 without bleeding into its neighbour; navbar + Hero fill one screen.
- A Hero where moon, text and the section arrows never collide, at any desktop window size, and a moon that fits small screens.
- A memorable approach intro that never blocks content or interaction.
- Simple, consistent section navigation controls (fixed arrows) and a phone-usable navbar.
- A WebGL canvas whose cost does not grow with page length.
- All new behaviour is tunable by named constants and degrades to normal scrolling.

## Non-goals
- Projects carousel, project routes/pages, About rework, Tech Stack rework, new Contact section, footer: all spec 006. Section content in Projects, About, Tech Stack stays as it is today (only their sizing and snap-target role change).
- A back-to-top button (removed from scope; the up arrow covers going back).
- Mobile/tablet-specific polish beyond the navbar menu and a non-breaking layout.
- A fixed or sticky navbar, scroll-spy, a section-dots or progress indicator.
- Touch-swipe snapping (touch scrolling stays native).
- Section-transition 3D animations or characters (for example an astronaut moving between sections): a future spec. This spec only prepares the ground with the viewport-fixed canvas.
- Changing the 004 cel shader and outline constants, spin speed, pointer parallax magnitudes, or the `/viewer` page.
- New dependencies (see NFR-3).
- The user's final SVG artwork (a placeholder only, see Assets).

## Users/Use cases
- Desktop visitor wheels, swipes a trackpad, or uses keys: each gesture moves exactly one section.
- Visitor clicks Projects/About in the navbar or the section arrows: animated move; a second click mid-move redirects it.
- Visitor drags the scrollbar or finds text in the page: the page settles on the nearest section when idle.
- Visitor opens `/#about` from a bookmark or returns from `/viewer`: lands on About.
- Visitor on a phone, a short or narrow window, or with reduced motion: scrolls normally, sees no arrows; the navbar collapses into a menu on phone widths; the moon fits the screen.
- Visitor with WebGL off or reduced motion: sees the poster at the same size, with the same text wrap.
- Owner tunes snap, moon, intro and star behaviour by editing named constants and drops in their own arrow SVG without touching component code.

## Decisions (owner answers, treated as requirements)
- D-1 Small-screen moon: the desktop size rule is clamped with a floor and a side-margin ceiling (FR-19). On phones the moon is smaller than today and fully visible with a margin on both sides.
- D-2 Section arrows replace the Hero CTA arrow and the back-to-top button (FR-28 to FR-32). One asset: `src/assets/icons/arrow-down.svg`; the up arrow is the same SVG rotated 180 degrees. The SVG uses `currentColor`.
- D-3 Explicit clicks (navbar links, arrows, hash navigation) interrupt and retarget a running move. Wheel, trackpad and key input during a move is still ignored (FR-7).
- D-4 Touch scrolling stays native, including on touch devices at 1024x700 or larger (FR-5).
- D-5 Sections only need to fill at least 100 svh and be snap targets in this spec; 006 redesigns them to fit one screen. Only a short no-clipping safeguard is kept (FR-17).
- D-6 Reduced-motion desktop windows keep the full-screen section layout (no snapping, no Lenis, no arrows) (FR-16, FR-18).
- D-7 After a non-snap scroll, the page settles on the nearest section once idle (FR-10).
- D-8 Poster and live outline thickness may differ on small windows (accepted; 004 FR-16 amended).
- D-9 The canvas is fixed to the viewport (FR-38 to FR-42).
- D-10 Touch settle (owner): touch devices at or above the snap thresholds also settle to the nearest section after native touch scrolling goes idle. Touch scrolling itself stays native and is never intercepted. The settle does not run while a touch is held, and inertial momentum must finish first (scroll idle for `SNAP_SETTLE_DEBOUNCE_MS`) (FR-5, FR-10).
- D-11 Nested scrollers (owner confirmed): nested scrollable elements opt out of wheel snapping with an explicit marker (`data-lenis-prevent` / `data-snap-ignore`) instead of layout reads (FR-5, NFR-2). No such element exists today; spec 006 must mark any nested scroll area it adds.

## Functional requirements

### Snap scrolling
- FR-1: Snap targets are the home sections in DOM order: Hero (target is page top, `scrollY = 0`, including the navbar), Projects, About, Tech Stack. Targets are discovered from the DOM (a marker such as a data attribute), not hard-coded by id, and each declares its display label (for example Hero, Projects, About, Tech Stack) through that marker, so spec 006 can add or remove sections without editing snap or arrow logic.
- FR-2: Snapping is active only when all hold: route is `/`; `window.innerWidth >= SNAP_MIN_WIDTH_PX` and `window.innerHeight >= SNAP_MIN_HEIGHT_PX`; `prefers-reduced-motion` is not `reduce`. Thresholds are named constants in one module, are in CSS px (so browser zoom changes them), and are evaluated live.
- FR-3: When active, one wheel or trackpad gesture (excluding Ctrl+wheel) animates to the next snap point (delta down) or previous (delta up) and the native scroll for that event is prevented. At the first or last target, further input in that direction does nothing.
- FR-4: When active, these keys do the same as FR-3: PageDown, PageUp, ArrowDown, ArrowUp, Space (next), Shift+Space (previous); Home goes to the first target and End to the last (one animation each). Keys are not intercepted when a modifier (Ctrl, Alt, Meta) is held, when the event is already `defaultPrevented`, when the target is an `input`, `textarea`, `select` or `contenteditable`, or when the focused element natively uses the key (Space on a `button`, `summary` or link activation; arrows on `role` widgets such as `menu`, `slider`, `tablist`).
- FR-5: Touch scrolling is never intercepted (native scroll, even at 1024x700 or larger; no `preventDefault` on touch events); only wheel and keys snap (D-4). Touch scrolling is still subject to the idle settle of FR-10 (D-10). A wheel event is also not intercepted when its target sits inside an element carrying the nested-scroller marker (`data-lenis-prevent` or `data-snap-ignore`, D-11); nested scrollable areas must carry the marker, and spec 006 must mark any nested scroll area it adds (no layout reads decide this, NFR-2). Middle-click autoscroll, text-selection dragging and the browser's own focus or find scrolling are not intercepted either (FR-10 handles where they end).
- FR-6: The move is a smooth animation of the window scroll position using `SNAP_DURATION_S` and `SNAP_EASE`. It ends exactly on the target (within 1 px), after clamping the target to the maximum scroll (so the last snap point is always reachable).
- FR-7: While a move runs, wheel, trackpad and key inputs are ignored: not queued, not applied natively. The page never skips a section or jumps. Explicit navigation is different: a click on a navbar link or section arrow, or a hash navigation (including browser back/forward and `ScrollToHash`), interrupts the running move and retargets it to the new target, starting from the current scroll position, ending exactly on the new target with only one animation running at any time. Retargeting never leaves the input lock stuck or released early.
- FR-8: Trackpad inertia must not cause a second move. After a move ends (including a retargeted or settle move), wheel events that belong to the same physical gesture (decaying inertia tail) are ignored. The plan chooses the mechanism (cooldown `SNAP_COOLDOWN_MS` and/or gesture-end detection using `SNAP_GESTURE_GAP_MS` and delta trend); both values are named constants. A new deliberate gesture, started after the wheel stream has paused, is recognised and moves one section.
- FR-9: The "current section" for wheel and key input is the snap point nearest to the live `scrollY` at the moment the input is accepted. The "displayed section" for the arrows (FR-28) is the destination of a running move, otherwise the nearest snap point. The native scrollbar stays visible and usable.
- FR-10: Settle. While snapping is active, after any scroll that was not produced by a snap move (scrollbar drag, keyboard focus scroll, find-in-page, middle-click autoscroll, touch scroll, scroll restoration on load, hash change landing mid-section) the page animates to a snap point once scrolling has been idle for `SNAP_SETTLE_DEBOUNCE_MS`. Rules:
  - The idle timer restarts on every scroll event, and no settle starts while a mouse button or touch is held down (it never fights an ongoing drag, including a scrollbar drag that pauses or a finger resting on the screen).
  - On touch devices at or above the snap thresholds (D-10), the settle runs after a native touch scroll once the touch has ended and the scroll, including inertial momentum, has been idle for `SNAP_SETTLE_DEBOUNCE_MS`; momentum is never cut short or fought, and the touch scroll itself is never intercepted.
  - Scroll events produced by the snap animation itself never start a settle.
  - The target is the nearest snap point, except when the scroll was caused by focus moving into an element (a `focusin` shortly before the scroll): then the target is the section containing the focused element, so the focused element stays visible.
  - Settling never calls `focus()`, `blur()` or changes `document.activeElement`. A focused element inside a section stays focused whichever section the page settles on; a focused text field keeps its caret and typed text.
  - The settle move uses the normal snap animation (FR-6), counts as a move for FR-7 (wheel and key input ignored while it runs, clicks retarget it) and for FR-8.
  - Settle is inactive wherever snapping is inactive.
- FR-11: Resize and threshold crossing:
  - Snap points are recomputed when layout changes (resize, fonts, zoom) without per-frame layout reads.
  - If the window crosses into active, handlers attach and the page re-aligns, without animation, to the section that was most in view.
  - If it crosses out of active (or reduced motion turns on, or the route leaves `/`), a running move or pending settle is cancelled cleanly at its current position, the input lock is released and handlers are removed.
  - A resize while a move runs does not leave a stuck lock: the move retargets the updated snap point or ends, and the page then rests on a snap point (via FR-10 if needed).
- FR-12: One scroll-to-section function (name fixed in the plan) is used by the navbar links `/#projects` and `/#about`, the section arrows, and `ScrollToHash`. When snapping is active it is the snap animation. When snapping is off and motion is allowed it uses Lenis `scrollTo` (or `scrollIntoView` if Lenis is absent), as in 002 FR-30. With reduced motion it scrolls instantly. No navigation path uses a different animation.
- FR-13: Deep links: loading `/#projects`, `/#about` or `/#tech-stack`, and navigating to `/#section` from `/viewer`, ends with that section's top at the viewport top (within 1 px) once layout has settled (fonts, poster, canvas) where snapping is active. Whether the arrival animates or is instant is a plan choice. An unknown hash leaves the page at the top with no error. Back/forward between hashes works. `ScrollToHash` keeps `SCROLL_OFFSET = 0` (navbar is not fixed). Where snapping is off, the existing 002 FR-30 behaviour applies.
- FR-14: Engine integration: no second smooth-scroll or scroll library (002 FR-29 still holds); Lenis smoothing and the snap animation never both animate the scroll position at once; `ScrollTrigger.update` and the scroll value used by the canvas (FR-39) keep working during snap animations; one-shot section reveals still play for the section arrived at. All listeners, ticker callbacks, tweens, timers and observers created for snapping, settling and arrows are removed on cleanup, and StrictMode double effects leave exactly one active set.

### Layout and sizing
- FR-15: The navbar stays in normal flow: not `fixed`, not `sticky`. It scrolls away with the Hero. The first snap point is the page top.
- FR-16: Where the layout threshold holds (`SNAP_MIN_WIDTH_PX` and `SNAP_MIN_HEIGHT_PX`, independent of reduced motion, D-6): Navbar height + Hero height equals one viewport (100 svh), and each other section is at least one viewport tall (100 svh). At 1920x1080 each rests exactly in view, shows no part of its neighbour, and has no overlap, negative margins or clipped content at its edges. Section content is vertically centred in its screen (minimal change; content itself is unchanged). The navbar height used for the Hero is the real rendered height, not a hard-coded value, and the sizing is done in CSS (no per-frame layout reads).
- FR-17: Safeguard only: sections use minimum height, never fixed height with `overflow: hidden`, so if a section's content is ever taller than the viewport at a snap-active size, nothing is clipped and all content stays reachable by wheel, keyboard, Tab and scrollbar. No dedicated design is required in this spec (current sections are shorter than one screen; 006 fits them to one screen).
- FR-18: Below the thresholds, and for reduced-motion users: no wheel or key interception, no settle, no section arrows, normal scrolling (Lenis smoothing stays as today unless reduced motion), no snapping. Layout does not break at 320 to 1919 px wide and 400 to 1080 px tall: no horizontal overflow, no clipped text, Hero content reachable.

### Hero
- FR-19: Moon size. Let `refRadius = MOON_REF_RADIUS_PX x MOON_SCALE_FACTOR x min(viewportWidth / HERO_REF_WIDTH_PX, viewportHeight / HERO_REF_HEIGHT_PX)`, with viewport size `window.innerWidth` and `window.innerHeight` (CSS px). The final body radius is `min(max(refRadius, MOON_MIN_RADIUS_PX), (viewportWidth - 2 x MOON_SIDE_MARGIN_PX) / 2)`. `MOON_REF_RADIUS_PX` is the radius the current code renders at 1920x1080 (about 405 px; the plan records the exact derivation from `moonFraming.js` and the 61 px navbar). Consequences the plan must preserve:
  - At 1920x1080 the body diameter is about 729 px (90% of about 810).
  - On desktop-size windows (at least `SNAP_MIN_WIDTH_PX` x `SNAP_MIN_HEIGHT_PX`) neither the floor nor the ceiling applies: `MOON_MIN_RADIUS_PX` is at most `refRadius` at 1024x700 (about 194 px) and the side-margin ceiling never binds there.
  - At 375x812 and 320x568 the moon is fully inside the viewport width with at least `MOON_SIDE_MARGIN_PX` of clear space on both sides, and is smaller than the current size (current diameter about 596 px at 375x812). The floor keeps it from shrinking to the plain rule's roughly 142 px. (amended 2026-10-21 by user request: below `HERO_WRAP_MIN_WIDTH_PX` the radius comes from the FR-23 column rule, which uses the same floor and side ceiling but also fits the text block above; the plain rule applies from 1024 up.)
  - The moon stays centred in the Hero box as today, never overflows the Hero on desktop-size windows (including short wide windows), and the 3 px outline from 004 is not part of the diameter.
- FR-20: The poster fallback (no WebGL, reduced motion, context loss, model failure, pre-live frame) follows the same function: the poster's visible moon diameter matches the live canvas moon within 5% at 1920x1080, 1440x900, 1366x768 and 375x812, with no visible size jump at the poster-to-canvas crossfade.
- FR-21: `HERO_REF_WIDTH_PX`, `HERO_REF_HEIGHT_PX` (1920, 1080), `MOON_SCALE_FACTOR` (0.9), `MOON_MIN_RADIUS_PX` and `MOON_SIDE_MARGIN_PX` are named constants in one module, documented by comment, editable by hand. Live canvas, poster and text wrap all read the same function and constants (one source of truth).
- FR-22: Hero text wraps around the moon. On windows at or above `HERO_WRAP_MIN_WIDTH_PX`, wherever the Hero text block (eyebrow, `h1`, paragraph) would overlap the moon disc, each text line is shortened so it follows the circular edge with at least `HERO_WRAP_MARGIN_PX` clearance (the margin includes the 3 px outline). Text therefore always sits on the dark background and never over the moon. The wrap uses the moon's final size (FR-19), is static during the intro growth (no reflow while the moon scales), is recomputed on resize and zoom, and does the same with the live canvas, the poster, or neither. Text stays in the DOM as normal text (selectable, readable by screen readers, heading keeps `aria-label` per 002 FR-27).
- FR-23 (amended 2026-10-21 by user request): Below `HERO_WRAP_MIN_WIDTH_PX` (default 1024 px, phone and small tablet widths, including landscape phones) the Hero is a single column and the text never overlaps the moon (text over the pale moon face has about 1.3-1.5:1 contrast). Top to bottom: navbar clearance (`--nav-h`), eyebrow + `h1` + paragraph (current type scale, fully visible), a gap of `HERO_COLUMN_GAP_PX` (24), the moon fully below the text, `HERO_COLUMN_BOTTOM_PX` (24) bottom space. The moon is horizontally centred. Moon radius in this mode (replaces the FR-19 rule, final radius, static during the intro): `R = min(max(fitR, MOON_MIN_RADIUS_PX), (viewportWidth - 2 x MOON_SIDE_MARGIN_PX) / 2)` with `fitR = (innerHeight - navH - textH - HERO_COLUMN_GAP_PX - HERO_COLUMN_BOTTOM_PX) / 2`, `navH` the navbar height and `textH` the measured text block height, so text + gap + moon diameter fit the viewport height whenever `fitR` is at least the floor. Fallback (decision, needs user confirmation): when `fitR` is below the floor (for example 812x375 or 568x320), the moon keeps the floor radius and the Hero grows taller than the viewport (min-height, never fixed), so the page scrolls normally; text and moon still never overlap. The moon centre in this mode is the centre of the moon slot below the text, not the Hero centre; live canvas and poster share that centre and size (FR-20). The moon intro animation (FR-24) and desktop (at or above `HERO_WRAP_MIN_WIDTH_PX`) behaviour (FR-19, FR-22) are unchanged. The "View projects" button is removed everywhere; below the snap thresholds there is no arrow control and the page scrolls normally.
- FR-24: Moon approach intro. The moon (live canvas and poster) starts at `MOON_INTRO_START_SCALE` (0.6) of its final scale and grows to 1.0 over `MOON_INTRO_DURATION_S` (3 s), about its own centre, using GSAP. Both are named constants editable by hand, with comments. Ease is a named constant (default decelerating ease-out). Only transform-type properties are animated (`transform` on the poster, object scale on the canvas); the moon's centre does not move. The 004 outline thickness stays constant in CSS px.
- FR-25: Sequence. The moon animation runs first. The existing Hero text intro (eyebrow, heading words, paragraph, then the down arrow of FR-28 in the old CTA slot, with the existing timings) starts when the moon animation ends. Total intro is about 5 s (3 s moon plus about 2 s text). The previous `[data-stage]` fade/scale-from-0.94 tween is replaced, so the stage is never animated by two systems. Where the arrow does not exist (snapping inactive) that slot is skipped.
- FR-26: The intro plays once per page load. Returning from `/viewer` shows the final state without replay. With React StrictMode double effects exactly one timeline plays and an unfinished one may restart cleanly (same guard idea as today). With `prefers-reduced-motion: reduce` there is no animation: the moon is at final scale and all text is at its final state from first paint.
- FR-27: Intro never gates content. Text "from" states are applied by JS only (no default CSS `opacity: 0`, no `visibility: hidden`, no `pointer-events: none`), so text is in the DOM at first paint; the navbar is never animated; the down arrow is clickable during the intro. The moon timeline does not wait for the lazy 3D chunk or model: it starts when the Hero mounts, drives the poster at once, and the live canvas joins at the current progress when ready (no size jump, per FR-20). If JS fails, everything shows in its final state. Scrolling away from the Hero during the intro, or a deep link to another section, must not error; the Hero is in its final state when the user returns.

### Section arrows
- FR-28: While snapping is active, two icon controls are shown, both fixed to the viewport and identical in look on every section: a down arrow at bottom-centre (goes to the next section) and an up arrow at top-centre (goes to the previous section), each offset from the edge by `SECTION_ARROW_OFFSET_PX` (plus `env(safe-area-inset-*)`). The up arrow is the same SVG rotated 180 degrees (CSS transform), so one asset serves both. On the displayed section (FR-9): the first section (Hero) shows only the down arrow, the last section (Tech Stack) shows only the up arrow, and every other section shows both. Both are positioned identically on every section (within 1 px) and are the only elements positioned there. The navbar is in flow, so the top-centre arrow appears only on sections 2 and later, where the navbar has scrolled away.
- FR-29: Behaviour. Down goes to the next section, up to the previous, through the shared scroll-to-section function (FR-12). A click interrupts and retargets a running move (FR-7); next/previous are relative to the displayed section (FR-9), so clicking repeatedly walks one section per click and never skips or goes beyond the ends. Visibility rules follow FR-9: the arrows' state is set when a move starts (destination) and kept correct at rest and after settle; the plan may time the up arrow's reveal so it does not overlap navbar items while the navbar is still scrolling away. The URL handling (hash update or not) is a plan choice; it must not reload the page, must not add history entries that break Back (replace instead of push for arrow clicks), and no arrow ever points at a missing section. The arrows exist only on `/` while snapping is active (FR-2): hidden and removed from the tab order and accessibility tree on smaller windows, with reduced motion, and on `/viewer`; turning snapping off at runtime removes them immediately.
- FR-30: Accessibility and states. Each arrow is a link or button with an accessible name built from the destination label (FR-1), for example "Next section: Projects" and "Previous section: Hero", updated whenever the displayed section changes; the icon is `aria-hidden`. Each has a hit area of at least 44x44 px, distinct hover, `:focus-visible` and active states using theme tokens and CSS transitions (no hover dependence), and a logical, documented tab order that never traps focus. When an arrow is hidden it is not focusable, not in the accessibility tree and not clickable. If activating (or any state change) hides the focused arrow, focus moves to the destination section's heading or container (programmatically focusable, `preventScroll`), never to `<body>`; the same applies when snapping turns off while an arrow has focus. At rest on each section, at 1920x1080, 1920x700, 1440x900, 1366x768, 1024x768 and 1024x700, the arrows do not overlap the moon disc (with `HERO_WRAP_MARGIN_PX` clearance), hero or section text, or interactive content.
- FR-31: Icon asset (see Assets): the arrow comes from `src/assets/icons/arrow-down.svg`, a clearly marked placeholder (a comment inside the file says "PLACEHOLDER, replace with owner SVG") until the user supplies theirs. There is no `arrow-up.svg`. Replacing the file at that path, with the same filename, needs no component code change. ### Viewport-fixed canvas
- FR-38: Fixed canvas. On `/`, exactly one R3F `<Canvas>` is fixed to the viewport (`position: fixed`, filling the viewport: CSS width and height equal to the visible viewport, `window.innerWidth` x `window.innerHeight` within 1 px), behind all page content (below sections and text in z-order), mounted from `HomePage.jsx` through the same lazy boundary. It replaces the page-tall canvas. Its size does not depend on page or document height, changes only on viewport resize or zoom, and does not change while scrolling. It adds nothing to document scroll height and no horizontal overflow. It stays decorative and non-interactive: `aria-hidden="true"`, `tabIndex=-1`, no `role`, `pointer-events: none`, R3F events off, never covering or intercepting any interactive content or gesture (003 FR-29 unchanged).
- FR-39: Moon anchoring. The moon stays visually anchored to the Hero: its on-screen centre is the Hero box centre in viewport coordinates, so as the page scrolls it moves up and out of view exactly in step with the Hero content and returns the same way. It must not lag the DOM: the Hero position is computed from cached page-space metrics (measured by observers, not per frame) minus the live scroll value, and that scroll value is the same value the scroll engine (Lenis, the snap animation, `ScrollTrigger`) applies in the same tick, read in the frame that renders (no stale value from a previous frame). Native compositor-thread scrolling that cannot be synchronised (for example a scrollbar drag) may show at most a single-frame offset and must settle to 0 offset at rest; the plan documents this limit. The moon's outline follows the moon in the same frame (004 FR-12). The moon is hidden and its spin and moon-only `useFrame` work are skipped while the Hero is out of view (003 FR-33), and scrolling back causes no rotation jump. Moon size and intro follow FR-19 to FR-24.
- FR-40: Stars. The starfield stays in WebGL with its slow drift and fine-pointer parallax (003 FR-17, FR-32) and is laid out over the fixed canvas. Scroll parallax is re-expressed for a fixed canvas: stars shift vertically with the scroll value by at most `STAR_SCROLL_PARALLAX_FACTOR` times the scroll distance (a small named factor), and the layer wraps seamlessly (for example modulo the canvas height with two copies) so no gap or pop appears at the top or bottom edge at any scroll position from 0 to the maximum. Point caps stay at most 2000 desktop and at most 800 coarse pointer or width under 768 px (003 D-20); because the canvas now covers one screen instead of the whole page, the plan sets the point count so on-screen star density at 1440x900 stays similar to today (within about 25%), within those caps, and records the chosen approach. Stars use preallocated state only (no per-frame allocation), read scroll from the stored value (no layout reads) and are not regenerated on every resize.
- FR-41: Unchanged behaviour: fallback states (no WebGL2, shader or model failure, context loss and restore, poster, `.hero-frame` gradient, plain `bg-ink` elsewhere), loop pause on `document.hidden` and context loss with no jump on resume, reduced motion (no canvas, poster only), lazy chunk boundary (no three/R3F in the entry chunk), disposal on unmount and StrictMode double mount, `/` to `/viewer` round trips. After a context restore the moon re-anchors correctly without a reload.
- FR-42: DPR and buffer limits for a viewport-sized buffer. The page-height cap (003 D-19, FR-35: CSS `maxHeight` and the `capCssHeight` behaviour for page height) is removed as obsolete. `DprController` and `computeDpr` remain, with the same `DPR_MAX` and pixel budgets, now applied to the viewport size. If the viewport width or height at DPR 1 exceeds the device's maximum buffer dimension, the canvas falls back to the poster (as 003 FR-35 did for width). `scripts/check-buffer-limits.mjs` (`npm run check:buffer`) is updated: cases that assumed page-tall canvases (for example 1920x4000, 375x4500, 375x6000) are replaced by viewport-sized cases (for example 1920x1080, 1440x900, 2560x1440, 3840x2160, 375x812, and a viewport larger than the device limit), including that 1920x1080 and 1440x900 reach `min(deviceDpr, DPR_MAX)` under the desktop budget. The effective DPR at 1920x1080 and at 1440x900 with an emulated device DPR of 2 is therefore 2 (not cut by the budget).

## Non-functional requirements
- NFR-1 Accessibility: all new controls are keyboard operable; focus rings visible on the dark background (3:1, 002 FR-6); screen-reader names per FR-30 and FR-35; reduced motion handled as in FR-2, FR-18, FR-24 to FR-26, FR-32, FR-35; no keyboard trap (Tab always moves on; snapping and settling never block Tab or the browser's own focus scroll, and never move focus); the document order still gives one `h1` and logical headings (002 NFR-2).
- NFR-2 Performance: no layout reads (`offsetHeight`, `getBoundingClientRect`, `scrollHeight`, `getComputedStyle`) inside per-frame callbacks (rAF, `gsap.ticker`, scroll, wheel, `useFrame`); measurements are cached via `ResizeObserver`/`IntersectionObserver`/`matchMedia` and re-read only on change. During a snap animation at 1440x900 with the moon in view there are no long tasks over 50 ms and no dropped-frame bursts in a DevTools performance trace; the wheel handler does O(1) work. Animations use `transform`/`opacity` except the scroll position itself. No per-frame allocation in new `useFrame` code (004 FR-20 still holds).
- NFR-3 Dependencies: none added. If the plan finds one is truly needed it must say so explicitly, justify it and pin it exactly (004 D-13 style). No second smooth-scroll or animation library (002 NFR-5).
- NFR-4 Structure: snap logic (input, settle), the scroll-to-section function, the section arrows, the menu and the moon-size/wrap function are separate single-purpose files (001 NFR-4, 002 NFR-6). Three/R3F imports stay inside `src/three/` and the lazy chunk (003 NFR-1).
- NFR-5 Canvas cost: the drawing buffer is one viewport (constant, independent of page length); render cost per frame does not change with the number or height of sections. The outline and any offscreen target stay within the viewport (004 FR-14 holds trivially).
- NFR-6 Consistency: one source of truth for the snap thresholds (JS and CSS agree; no flash of a mismatched layout on load) and for the moon final-size function (canvas, poster, wrap).
- NFR-7 Theme: new UI uses the existing `@theme` tokens only (002 FR-1); no new colours or fonts.
- NFR-8 Build: `npm run build`, `npm run lint` and `npm run check:buffer` exit 0 with no new warnings; no console errors or warnings on `/` and `/viewer`.

## Edge cases (required behaviour)
- Resize while a move runs, threshold crossing both ways: FR-11.
- Retargeting: a navbar or arrow click, or a hash navigation, during a move retargets without a jump; wheel and keys during the move are ignored: FR-7. Clicking the arrow for the section already shown does nothing visible and leaves no stuck lock.
- Settle versus focus: a Tab-focus scroll settles to the focused element's section without moving focus; a scrollbar drag away from a focused element settles to the nearest section and focus stays on the element; a focused text field keeps caret and text; no settle while the mouse button is held: FR-10.
- Focused input inside a section (none today; spec 006 adds a contact form): keys and wheel are not hijacked per FR-4 and FR-5.
- Browser zoom: thresholds are in CSS px, so zooming in can turn snapping off (arrows disappear, FR-29) and zoom out can turn it on (FR-11); moon scale, wrap, snap points and canvas size are recomputed; the page rests on a snap point after a re-align.
- Hash navigation: FR-13; deep link to a lower section runs the Hero intro unseen (FR-27) and the Hero is final when the user returns.
- Reload or back/forward with scroll restoration mid-page: the browser restores the position and the page settles once idle (FR-10).
- StrictMode double effects: FR-14 and FR-26.
- WebGL fallback or poster: FR-20, FR-22, FR-24 with the poster only; context loss mid-intro: the poster shows at the current scale and the intro keeps its timing; after restore the canvas moon re-anchors (FR-39, FR-41).
- Ctrl+wheel (browser zoom), middle-click autoscroll, text-selection dragging: not intercepted (FR-3, FR-5).
- Phone widths (amended 2026-10-21 by user request): the moon uses the column rule of FR-23 (floor, side ceiling, fit under the text) and sits below the text, never behind it; landscape phones keep the floor radius and the Hero grows taller than the viewport; no arrows, normal scrolling.
- Hero text block taller than the Hero once wrapped at a small desktop size (for example 1024x700): the plan must keep text from overlapping the moon and keep navbar + Hero within one screen where snapping is active (for example by responsive type size), and report any size where that is not possible.
- Outline thickness: the live outline stays 3 CSS px while the poster's outline scales with the poster (accepted, D-8).
- Native scrollbar drag with a fixed canvas: at most a one-frame moon offset while dragging (FR-39).
