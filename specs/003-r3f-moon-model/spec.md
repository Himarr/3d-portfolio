# 003 R3F Migration and Moon Model

## Summary
Migrate the hero 3D scene from imperative Three.js (`src/three/createPlanetScene.js` driven by `src/three/PlanetCanvas.jsx`) to React Three Fiber (`@react-three/fiber` + `@react-three/drei`), and replace the procedural-shader planet with the authored moon model `src/assets/3D/moon.glb`. A reusable, generic `Model` component (imported `.glb` URL in, rendered scene out) is introduced so the owner can add their own models later; the moon is its first consumer. The fresnel atmosphere glow is dropped. The static poster `src/assets/hero-planet-poster.png` is regenerated from the moon so the fallback frame matches the live scene. All 002 hero guarantees (lazy chunk, pausing, fallbacks, disposal, accessibility, performance) keep holding unless explicitly superseded below. Cel/toon shading is out of scope (next spec).

Scope change 2026-10-20 (D-14 to D-18, resolved and refined by D-19 to D-26): the starfield is no longer hero-only. One page-tall decorative canvas, mounted from `HomePage.jsx`, spans the whole home page content height behind all content, so stars show behind every section; the moon stays a hero object that scrolls away with the hero. Where this conflicts with earlier FR/AC text, the amendments in "Scope change: full-page starfield" and the "Superseded or amended" section win.

Brownfield on 001 and 002: Vite 8, React 19 (StrictMode on in `src/main.jsx`), react-router-dom 7, Tailwind v4, `three` ^0.186.1 (installed 0.186.1), GSAP + Lenis, oxlint.

## Goals
- The whole hero scene is R3F: moon, starfield, slow rotation, pointer parallax, offscreen/hidden pausing, context-loss handling and disposal.
- The moon renders unlit with its embedded texture as authored; no lights needed.
- A generic, reusable model loader (`Model`) with cached loading, a Suspense loading state, error fallback to the poster and clean disposal.
- A short convention doc for adding models (location, Blender glTF export settings, size/texture budget).
- Poster regenerated from the moon, with provenance recorded.
- Imperative scene code and procedural planet/atmosphere shaders removed.
- Stars visible behind every section from top to bottom of `/` (one page-tall canvas, D-14), with subtle scroll parallax and slow drift (D-16), within WebGL drawing-buffer limits and a mobile GPU budget (D-18, D-19).

## Non-goals
- Cel/toon shader, outlines, post-processing (next spec).
- `/viewer` content, orbit controls, model picker; `/viewer` stays "Coming soon" (002 AC-18).
- Draco / meshopt decoder wiring (possible later spec).
- Atmosphere glow or any new visual feature (glow, lights, bloom, shadows, environment maps).
- Models served from `public/models/` or runtime URLs; only bundled imports from `src/assets/3D/`.
- Changes to Navbar, Projects, AboutMe, TechStack, ViewerPage, GSAP/Lenis setup (`src/lib/gsap.js`, `src/components/SmoothScrollProvider.jsx`), hero copy or theme tokens. Allowed by the scope change, minimum only: `src/pages/HomePage.jsx` (canvas mount and status provider, D-21), `src/components/sections/Hero.jsx` (D-11 as widened by D-21 and D-22) and one small new context module. `src/App.jsx`, `src/index.css` and section background classes are not expected to change (sections currently have no opaque background); if the plan finds a change needed it must list it and justify it under FR-28. Copy, Navbar behaviour and the GSAP/Lenis setup stay untouched.
- A CSS/DOM starfield fallback for the rest of the page (D-17), a viewport-fixed backdrop, multiple canvases, per-section canvases, tiling or windowing of the starfield (D-19).
- New visual features beyond stars (nebula, shooting stars, star colour changes).
- Synthetic huge-page testing (D-25).

## Decisions (owner, resolved)
- D-1 Atmosphere glow: dropped. The fresnel atmosphere shell and `src/three/shaders/atmosphere.frag.glsl` are removed; no replacement glow.
- D-2 Scale and framing: the moon keeps the current planet's on-screen size and camera framing (today: unit-radius sphere, perspective camera FOV 40 at z = 3.6, group axial tilt -0.18 rad on Z, per `src/three/createPlanetScene.js`). The requirement is the on-screen result (diameter, position, tilt); the plan may reproduce it with a different projection.
- D-3 Rotation: the GLB node's baked Y-rotation quaternion is the starting orientation; slow continuous spin is applied on top of it (not replacing it).
- D-4 Model location: models are bundled imports from `src/assets/3D/` (hashed filenames, build-time error on a bad path). `Model` takes the imported URL. `public/models/` is out of scope.
- D-5 Peer ranges (verified on npm by orchestrator, 2026-10-20): `@react-three/fiber` 9.8.2 peers `react >=19 <19.4`, `react-dom >=19 <19.4`, `three >=0.156` (expo/react-native peers are native-only); `@react-three/drei` 10.7.9 peers `react ^19`, `react-dom ^19`, `three >=0.159`, `@react-three/fiber ^9.0.0`. Repo has react/react-dom ^19.2.8 and three ^0.186.1, so compatible. Pin both packages exactly (`9.8.2`, `10.7.9`, no caret). The React `<19.4` upper bound is a constraint on future React upgrades.
- D-6 Poster provenance references: 002 FR-33 (provenance) and FR-12 (poster). The brief's "FR-31" was a typo.
- D-7 `.glb` imports: a one-line `assetsInclude: ['**/*.glb']` in `vite.config.js` is approved (no `?url` suffix needed).
- D-8 Draco: `Model` disables Draco explicitly so no third-party/CDN request occurs.
- D-9 Poster file name stays `src/assets/hero-planet-poster.png`.
- D-10 Canvas component rename: decided in plan.md. Superseded in scope by D-11 and D-21 (the canvas is page-level).
- D-11 `Hero.jsx` edit scope (owner, 2026-10-20), widened by D-21 and D-22: allowed edits are the FR-25 provenance comment; removing the in-hero canvas mount (lazy import, Suspense, canvas JSX); consuming the canvas-status context (D-21) to show/hide the poster; and the removal of the `hero-frame` class from the section (D-22; amended 2026-10-21 by user request). No copy, heading, CTA, intro timeline or other change.
- D-12 Model cache lifetime (owner, option A, free on leave): on the last unmount the moon's geometry, materials and textures are disposed and `useGLTF.clear(url)` is called. Returning from `/viewer` re-fetches `moon.glb` from the browser HTTP cache (no new network download, hashed filename) and re-parses it; re-parsing is expected.
- D-13 Baseline artifacts (owner): before-migration screenshots go in the new folder `src/assets/img/` (not imported by app code, so not bundled); `baseline.md` (build sizes) stays in `specs/003-r3f-moon-model/`.
- D-14 Canvas (owner, 2026-10-20): ONE page-tall canvas spans the full page content height, sits behind all page content, and scrolls with the page (not a viewport-fixed backdrop). It stays decorative: `aria-hidden`, `pointer-events: none`, behind content in z-order. It tracks document height changes (resize and content changes) via an observer. It must not affect layout or scroll height. Sections are transparent over the App shell's `bg-ink`; the stars must be visible behind them. Lenis smooth scroll must keep working.
- D-15 Moon (owner): the moon belongs to the hero and scrolls away with the hero section, keeping its current framing and size relative to the hero (D-2). Only stars remain behind the other sections.
- D-16 Star motion (owner): subtle scroll parallax (stars shift slightly relative to scroll) plus slow constant drift, plus the existing fine-pointer parallax (FR-17). Because stars drift constantly, the render loop runs whenever the tab is visible and the canvas is usable; it pauses on `document.hidden` and context loss. The 002 "pause when offscreen" rule (002 FR-18) is amended: the canvas is never fully offscreen, but moon spin and other `useFrame` work for invisible objects is skipped (moon while the hero is offscreen). Reduced motion: no drift, no scroll parallax, no spin; 002 reduced-motion fallback semantics (static poster, no canvas) are kept.
- D-17 Fallback (owner): on reduced motion, no WebGL, model load failure or context loss, the hero shows the static poster as today and the rest of the page falls back to the plain dark background (`bg-ink`). No CSS starfield.
- D-18 Drawing-buffer limits (orchestrator-added hard constraint): the page-tall canvas must never request a drawing buffer larger than the device allows (`gl.MAX_RENDERBUFFER_SIZE`, `gl.MAX_VIEWPORT_DIMS`; often 4096 to 16384 px, lower on mobile). Effective DPR is reduced below the 002 cap of 2 (down to 1) as needed so `cssHeight * DPR` and `cssWidth * DPR` stay within limits.
- D-19 Over-limit page (owner, 2026-10-20, former Open question 1, option a): if the page content height at DPR 1 exceeds the largest drawing-buffer height the device allows, the canvas height is capped at that limit (computed at DPR 1) and content below the cap shows the plain `bg-ink` background. No tiling, no windowing, no hero-only fallback, no full fallback. The owner notes this is effectively never hit on the real page.
- D-20 Star density (owner, former Open question 2): keep the absolute caps (at most 2000 points desktop, at most 800 on coarse pointer or width under 768 px) regardless of page height. The plan must check visual density on the real page and the result is noted at verification.
- D-21 Mount and status (owner, former Open question 3): a single lazy canvas is mounted in `src/pages/HomePage.jsx` (route `/` only). Its status (`live` / `fallback`, plus the initial `idle`) is shared with `Hero.jsx` through a small React context. `Hero.jsx` may consume this context to show or hide the poster (D-11 widened).
- D-22 Hero frame (owner, former Open question 4; amended 2026-10-21 by user request, supersedes the earlier same-day "always visible" amendment): the `.hero-frame` element (CSS gradient and radial glow behind the moon) is REMOVED entirely. The hero is transparent in every state: once the canvas is live the page-wide stars show behind the hero; only the poster fades out at the 700 ms handoff. Before live and in fallback the hero shows the poster over the plain page background (`bg-ink`), with no frame.
- D-23 Motion magnitudes (owner, former Open question 5): the planner chooses subtle values for drift, scroll parallax and pointer parallax as named constants in plan.md; the owner tunes them after a visual check.
- D-24 Canvas height (owner, former Open question 6): the canvas height follows the document content height only (no `svh`/`dvh`, no `window.innerHeight` for sizing), so mobile URL-bar toggling does not reallocate the drawing buffer.
- D-25 Testing correction (owner): no synthetic 20,000 px or 60,000 px tall-page tests. Canvas width comes from the user's screen width and height follows from that width and the real page content. Buffer limits are verified on the real `/` page at representative widths and DPRs (AC-25); the over-limit cap logic (D-19) is verified by code review and a unit-level check of the clamp function (AC-30), not by building a giant page.
- D-26 Canvas top edge (planner-derived consequence of D-21, flagged for owner): because the canvas is mounted by `HomePage.jsx`, it spans the HomePage content box, which starts immediately below the Navbar (the Navbar is opaque `bg-ink`, so the first ~61 px of the document were never going to show stars) and ends at the document bottom. "Page height" in FR-26/FR-27/FR-34 means this content box.

## Users/Use cases
- Visitor lands on `/` and sees the textured moon slowly rotating in the hero, with the same layout, text, CTA and starfield as before.
- Visitor with reduced motion, no WebGL, a failed model load or a lost GPU context sees the static poster (now a moon) and a fully working page.
- Visitor scrolls the whole page and sees stars behind every section, drifting slowly and shifting subtly with scroll, while the moon leaves with the hero.
- Owner drops a new `.glb` into `src/assets/3D/`, changes one import in the hero scene, and it renders with no change to `Model` code.

## Functional requirements

### Dependencies and structure
- FR-1: `@react-three/fiber` 9.8.2 and `@react-three/drei` 10.7.9 are added to `dependencies`, pinned exactly (D-5). plan.md records the versions and peer ranges (compatible with React 19.2 and `three` 0.186) and notes the React `<19.4` bound. No other 3D/runtime dependency is added (supersedes 002 NFR-5 only for these two packages).
- FR-2: `three`, `@react-three/fiber` and `@react-three/drei` are imported only from files inside `src/three/`, and those files are reachable from the app only through a `React.lazy` boundary in `src/pages/HomePage.jsx` (D-21). Drei is used via named imports only, and only helpers actually used are imported.
- FR-3: `src/three/createPlanetScene.js`, `src/three/shaders/planet.vert.glsl`, `src/three/shaders/planet.frag.glsl` and `src/three/shaders/atmosphere.frag.glsl` are deleted once the R3F scene replaces them. No file in `src/` constructs `WebGLRenderer`, calls `requestAnimationFrame` for 3D rendering, or imports the deleted files. (Supersedes 002 FR-14.)

### Hero canvas (R3F, carries 002 requirements)
- FR-4: The page canvas component (named in plan.md, D-10) renders a single R3F `<Canvas>` and reports `'idle' | 'live' | 'fallback'` to `HomePage.jsx`, which publishes it through the canvas-status context (FR-38) so the poster fade-out in `Hero.jsx` is driven by it. `'live'` is reported only after a frame was rendered with the model loaded. (002 FR-13, FR-12)
- FR-5: Canvas configuration: DPR range `[1, 2]` further limited by FR-34 (002 FR-17), alpha/transparent background so the page shows through (002 FR-12), antialiasing on, moon framing per D-2.
- FR-6: Resize is handled by an observer on the canvas container with no layout reads per frame, no per-scroll measurement and no resize loop (R3F's built-in resize measurement is acceptable if it uses an observer and its scroll-based re-measure is disabled). (002 FR-17)
- FR-7: Rendering is paused when `document.hidden` is true and resumes when visible, by gating the R3F frameloop (e.g. `frameloop` `'never'` vs `'always'`). While paused, no `useFrame` callback runs. Resume causes no jump. The offscreen-pause part of 002 FR-18 is amended by FR-33. (002 FR-18)
- FR-8: No per-frame allocation: `useFrame` callbacks create no objects, arrays, vectors, colours or closures; all are preallocated or held in refs. (002 FR-19)
- FR-9: Context loss is handled via the canvas element's `webglcontextlost` (calls `preventDefault`, pauses the frameloop, reports `'fallback'`) and `webglcontextrestored` (resumes and reports `'live'` after a rendered frame, or leaves the poster). Listeners are removed on unmount. (002 FR-20)
- FR-10: The canvas is decorative: `aria-hidden="true"`, not focusable (`tabIndex=-1`), no `role`, `pointer-events: none` on the canvas and its wrapper, and R3F's pointer event system does not intercept pointer events over text or the CTA. (002 FR-22)
- FR-11: Unsupported WebGL (feature detection before mounting `<Canvas>`), renderer creation failure, shader compile errors (`gl.debug.onShaderError` or equivalent) and model load failure all result in `'fallback'` (static poster), with no uncaught errors and the page unaffected. Model load failure is caught by an error boundary around the 3D content. (002 FR-12, FR-23)
- FR-12: Reduced motion (`prefers-reduced-motion: reduce`, existing `usePrefersReducedMotion`) still prevents the canvas and the 3D chunk from mounting; poster only. The gate now lives in `HomePage.jsx`. (002 FR-31)
- FR-13: Full disposal on unmount, including route change to `/viewer` and StrictMode double-mount: renderer disposed and context released, canvas removed from the DOM, observers disconnected, all listeners (visibility, pointer, scroll, resize, blur, context events) removed, and model/starfield geometries, materials and textures disposed so that `renderer.info.memory` returns to baseline (see AC-7). A dev-only hook (guarded by `import.meta.env.DEV`, like the existing `window.__planetInfo`) exposes `renderer.info.memory` and the buffer figures needed by AC-25. (002 FR-21, NFR-8)

### Moon and scene content
- FR-14: The hero renders `src/assets/3D/moon.glb` through `Model` (FR-18). The moon uses the GLB's own material (`KHR_materials_unlit` -> unlit, base colour texture "Moon_BaseColor", double-sided) unchanged; the scene contains no lights and the moon's appearance does not depend on lights. No custom shader material is applied to the moon in this spec.
- FR-15: Orientation: the GLB node's baked Y-rotation is preserved as the starting pose; continuous spin about the Y axis is applied on top (e.g. on a parent group), with one full turn taking at least 60 s. Spin is frame-rate independent (delta based, delta clamped as today). (002 FR-16, D-3)
- FR-16: Framing: the moon's on-screen diameter and position at 1440x900 and 375x812 match the current planet within about 5% (normalised to the current unit-radius sphere framing per D-2). (D-2)
- FR-17: Starfield and parallax carry over: stars are generated once from the existing seeded generator (mulberry32, same seed), at most 2000 points desktop and at most 800 on coarse pointer or width under 768px (002 FR-15). Pointer parallax: the moon tilts by at most +/-0.15 rad; stars shift by at most a small plan.md constant (D-23); input sampled at most every ~33 ms, smoothed in `useFrame`, active only with `(pointer: fine)`, and returns to the default pose on window blur (002 FR-16, FR-37).

### Reusable model loading
- FR-18: A generic `Model` component in `src/three/` takes an imported model URL (plus optional standard transform props) and renders the loaded glTF scene. It contains no moon-specific code. It is built on drei `useGLTF`, so while at least one consumer is mounted, loads of the same URL share one fetch and one parse. The cache does not outlive the last consumer (FR-21, D-12): after it unmounts, a later mount re-parses the model, with the file served from the browser HTTP cache.
- FR-19: Loading state: while the model loads, the 3D content is inside `<Suspense>`; the poster remains visible (status stays `'idle'`) and no layout shift occurs.
- FR-20: Error handling: a missing/invalid/corrupt model triggers the error boundary from FR-11, reports `'fallback'`, and logs at most one dev-mode error from project code. A bad import path fails `npm run build` (D-4).
- FR-21: Disposal: when the last consumer unmounts, the model's geometries, materials and textures are disposed (or the cache is cleared) so GPU memory returns to baseline, without breaking a later remount (StrictMode, return from `/viewer`). The plan must state how the `useGLTF` cache and disposal interact.
- FR-22: Importing `.glb` from `src/assets/3D/` yields a hashed asset URL in the build via `assetsInclude: ['**/*.glb']` in `vite.config.js` (D-7). `Model` explicitly disables Draco (D-8), so loading a model makes no request to third-party origins (e.g. no Draco decoder fetch from a CDN).
- FR-23: Swapping the model is a one-line change: replacing the moon import in the hero scene with another `.glb` from `src/assets/3D/` renders it with no change to `Model` code. The convention doc shows this as an example.

### Docs and assets
- FR-24: A short convention doc for adding models exists (location decided in plan; default `src/assets/3D/README.md`). It covers: file location and import pattern, the swap example (FR-23), Blender glTF 2.0 export settings (format `.glb`, +Y up, apply transforms, embedded textures, include normals and UVs, no cameras/lights, no Draco until a later spec), and a budget (default: at most 1 MB per `.glb`, textures at most 2048x2048, PNG or JPEG, at most ~50k vertices for hero use).
- FR-25: `src/assets/hero-planet-poster.png` is regenerated from the live R3F moon scene (transparent background, no starfield, same framing and default pose, same 1200x1200 size used by the `<img>` in `Hero.jsx`), via a dev-only capture path equivalent to the current `/?capture-poster` (dead code in production). The provenance comment in `Hero.jsx` is updated to "generated from this app's moon model scene on <date>; moon.glb provided by owner". (002 FR-12, FR-33)

### Scope change: full-page starfield (D-14 to D-26)
- FR-26: Single page-tall canvas (D-14, D-21, D-26). On `/`, exactly one R3F `<Canvas>` is positioned absolutely at the top of the HomePage content box (immediately below the Navbar), spanning its full width and its full height (subject to the D-19 cap), not `position: fixed`, behind all page content (below sections and text in z-order), scrolling with the page. It is mounted from `HomePage.jsx` through the lazy boundary (FR-2). It adds nothing to document scroll height and no horizontal overflow.
- FR-27: Height tracking (D-14, D-24). Canvas height follows the HomePage content height (document height) through an observer (`ResizeObserver`, no per-frame layout reads); viewport width resize, font load, route content and section height changes update the canvas size within one observer callback, with no resize loop and no feedback where the canvas itself changes the measured height. No `svh`, `dvh`, `vh` or `window.innerHeight` is used to size the canvas or its drawing buffer. (Refines FR-6.)
- FR-28: Visibility minimum (D-14, D-22). Stars are visible behind every section (Hero, Projects, AboutMe, TechStack) and the gaps between them once the canvas is live. No section has an opaque layer hiding the canvas: the `.hero-frame` element is removed and the hero is transparent (D-22; amended 2026-10-21 by user request). Sections keep their layout, copy and spacing. Opaque card surfaces (e.g. `bg-surface` project cards) and the Navbar's `bg-ink` are not changed. Exact edits are listed in plan.md.
- FR-29: Decorative and non-interactive (D-14). Page canvas and its wrapper: `aria-hidden="true"`, `tabIndex=-1`, no `role`, `pointer-events: none`, and R3F event handling not intercepting anything, so no text, link, button or scroll/touch gesture is intercepted. Text selection, focus order and Lenis smooth scroll (wheel, touch, keyboard, anchor navigation via `ScrollToHash`) behave as before. (Extends FR-10.)
- FR-30: Moon placement (D-15). The moon is positioned in the page canvas to coincide with the hero stage (same on-screen position and size as the poster and as FR-16, at 1440x900 and 375x812 at scroll 0) and moves with the page, so it scrolls out with the hero. Its placement follows hero position and size in page coordinates and updates on layout changes (resize, hero height change). It is not re-centred on the viewport at other scroll positions. Spin and its `useFrame` work are skipped while the hero is offscreen (FR-33).
- FR-31: Star layer (D-14, D-16, D-20). The starfield spans the full canvas height (not just the hero), is generated once from the existing seeded generator (mulberry32, same seed; FR-17), and keeps the point caps: at most 2000 points desktop, at most 800 on coarse pointer or width under 768px. The caps are absolute totals for the whole page regardless of page height (D-20). Stars are not regenerated on resize or content height change.
- FR-32: Motion (D-16, D-23). With motion allowed: (a) slow constant drift of the stars, frame-rate independent (delta based, clamped as in FR-15), with a drift speed constant in plan.md; (b) subtle scroll parallax: stars offset relative to scroll position by a bounded amount (max offset constant in plan.md, small relative to viewport height), driven by the scroll position without per-frame layout reads (scroll event or Lenis scroll callback stored in a ref); (c) existing fine-pointer parallax (FR-17). Under `prefers-reduced-motion: reduce` none of (a), (b), spin runs (FR-12 unchanged: no canvas, poster only). Preallocated state only, no per-frame allocation (FR-8).
- FR-33: Render loop gating (D-16; amends FR-7). The frameloop runs while `document.hidden` is false and the canvas is usable (not context-lost, not failed). It pauses on `document.hidden` and context loss and resumes without a jump in drift, spin or parallax. It does not pause on offscreen (the canvas is never fully offscreen). While the hero is offscreen (`IntersectionObserver` on the hero), the moon's spin and any moon-only `useFrame` work are skipped and the moon is not rendered (`visible=false` or equivalent); resume causes no rotation jump.
- FR-34: Drawing-buffer limits (D-18, D-19). At canvas creation and on every size change, the effective DPR is `min(devicePixelRatio, 2, maxDprForSize)` with a floor of 1, where `maxDprForSize` ensures `ceil(cssWidth * dpr)` and `ceil(cssHeight * dpr)` are each at most `min(gl.MAX_RENDERBUFFER_SIZE, gl.MAX_VIEWPORT_DIMS[0], gl.MAX_VIEWPORT_DIMS[1])`, and total pixels stay within the budget in NFR-6 (budget is met by lowering DPR; it never lowers DPR below 1). DPR is never raised above the 002 cap of 2 (amends FR-5). The drawing buffer is never requested above the device limit, even transiently; the canvas is created at DPR 1 and raised only after the size is known.
- FR-35: Over-limit behaviour (D-19). The canvas CSS height is capped at the largest drawing-buffer height the device allows at DPR 1 (`min(MAX_RENDERBUFFER_SIZE, MAX_VIEWPORT_DIMS[1])`). Content below the cap shows the plain `bg-ink` background; the rest of the page and the stars above the cap are unaffected. The cap is applied by the layout (CSS max-height) before the renderer sizes the buffer, so the browser or driver never silently clamps or fails. If the canvas CSS width alone exceeds the device limit at DPR 1 (not a realistic screen), the canvas falls back (FR-36).
- FR-36: Fallback split (D-17, D-22). In every fallback case (FR-9, FR-11, FR-12: reduced motion, no WebGL, shader error, model load failure, context loss) the hero shows the static poster over the plain page background (no frame; D-22, amended 2026-10-21 by user request), and every other part of the page shows the plain `bg-ink` background; no canvas remains in the DOM except during context loss/restore. Model load failure drops the whole page canvas (stars included), not only the moon. The status (FR-4, FR-38) still drives the hero crossfade; `'live'` still means a frame rendered with the moon loaded.
- FR-37: Route scope. The page canvas exists on `/` only and is disposed when navigating to `/viewer` (FR-13 and AC-7 unchanged). See Assumptions.
- FR-38: Status sharing and hero integration (D-21, D-22). A small React context (no `three` import) carries the canvas status from `HomePage.jsx` to `Hero.jsx`. `HomePage.jsx` owns the status state, the reduced-motion gate and the lazy mount. `Hero.jsx` reads the status: the poster is visible unless status is `'live'`; there is no hero frame element (removed, D-22; amended 2026-10-21 by user request), the hero is transparent in every state; the poster fades out via a transition that respects reduced motion. Outside a provider the status defaults to `'idle'`. No other `Hero.jsx` behaviour or copy changes.

## Non-functional requirements
- NFR-1: Entry chunk contains no `three`, `@react-three/fiber` or `@react-three/drei` code; the 3D code is in a separate lazy chunk. Chunk sizes (raw and gzip) of entry and 3D chunks are reported before (current build) and after the migration in verification.
- NFR-2: `npm run lint` and `npm run build` exit 0 with no warnings from project code; no runtime console errors or warnings on `/` and `/viewer` (002 NFR-7).
- NFR-3: Accessibility and performance outcomes from 002 are unchanged: hero text and CTA usable from first paint (002 FR-11), the 3D chunk never blocks hero text, no continuously animating offscreen content except as amended by FR-33 (002 NFR-4), 002 AC-4, AC-9, AC-10, AC-16, AC-17, AC-22 still pass.
- NFR-4: No memory growth after repeated `/` <-> `/viewer` navigation (002 NFR-8).
- NFR-5: Components stay per-file and single-purpose (002 NFR-6): `Model` (generic), the page canvas/scene components, star layer and small hooks are separate files under `src/three/`.
- NFR-6: GPU/fill-rate budget for the large canvas (D-18). Total drawing-buffer pixels (`canvas.width * canvas.height`) are capped at a budget set in plan.md (default: 16 million px desktop, 8 million px on coarse pointer or width under 768px); DPR is reduced (to a floor of 1) to meet it. Rendering is the star points (one shared geometry, see Assumptions) plus the moon; no post-processing, no extra render targets, no per-frame buffer re-uploads for stars (motion via transform). On a mid-range mobile device (or 4x CPU throttle plus emulated mobile) scrolling stays smooth with the main thread not blocked by 3D work beyond the frame budget.
- NFR-7: Scroll and layout cost. The observer and scroll handlers do no per-frame layout reads, no forced reflow, and cause no layout shift (CLS contribution 0 from the canvas). The canvas does not change `document.documentElement.scrollHeight`.
- NFR-8: Star density versus page height is bounded by the caps in FR-31 regardless of page length (a long page cannot raise point count or buffer size).

D-19 caps by the device limit only, as decided by the owner.
- (Planner, flagged) "Single `Points` object" in earlier text means one star geometry/layout; the plan may render it as two `Points` instances sharing the same positions so the constant drift can wrap seamlessly without a custom shader or per-frame buffer upload. Point count stays within the caps.

Star size is expressed in screen pixels. Colour, opacity and seed are unchanged.

- Normalising the moon to the unit-radius framing is done in the scene (by scale/centre), not inside `Model`; `Model` stays generic and accepts transform props.
- Spin speed stays at the current 90 s per turn (within the >= 60 s limit).
- The poster stays at `src/assets/hero-planet-poster.png` (file name kept even though it is now a moon).
